= FunClient

FunClient is a synchronous HTTP client for Java 21. HTTP transport depends only on a
small serialization contract; JSON support is an optional adapter.

== Modules and dependencies

* `funclient-core` — HTTP transport, models, `Serializer`, request bodies and response handlers.
* `funclient-serializer` — groups adapters and does not publish an artifact.
* `funclient-serializer/serializer-kotlinx` — JSON adapter using kotlinx.serialization.

[source,kotlin]
----
plugins {
    kotlin("jvm") version "2.4.0"
    kotlin("plugin.serialization") version "2.4.0"
}

dependencies {
    implementation("net.igsoft:funclient-core:0.7.0")
    implementation("net.igsoft:serializer-kotlinx:0.7.0")
}
----

The core can be used on its own with any implementation of `Serializer`.
The adapter exposes its core and JSON dependencies transitively. The serialization
compiler plugin is needed in applications that use generated `@Serializable` models.

== Requests and responses

[source,kotlin]
----
import java.net.URI
import kotlin.reflect.typeOf
import kotlinx.serialization.Serializable
import kotlinx.serialization.json.Json
import net.igsoft.funclient.FunClient
import net.igsoft.funclient.handler.ObjectResponseHandler
import net.igsoft.funclient.handler.TypedResponseHandler
import net.igsoft.funclient.model.*
import net.igsoft.funclient.serializer.kotlinx.KotlinxSerializer

@Serializable
data class Item(val id: Int, val name: String)

val serializer = KotlinxSerializer(Json {
    ignoreUnknownKeys = true
    // serializersModule = yourModule
})
val client = FunClient(serializer = serializer)
val responseType = typeOf<List<Item?>?>()
val request = Request(
    method = Method.POST,
    url = URI("https://example.com/items").toURL(),
    headers = Headers.builder().append(Headers.CONTENT_TYPE, "application/json").build(),
    body = Body.serialized<List<Item?>?>(listOf(Item(1, "first"), null)),
)
val response = client.execute(request)
val items = ObjectResponseHandler<List<Item?>?>(responseType)
    .handle(request, response, serializer)
val typedResponse = TypedResponseHandler<List<Item?>?>(responseType)
    .handle(request, response, serializer)
// typedResponse preserves status, headers and the declared type in its ObjectBody.
----

Use the `Body` factories to create request bodies:

[source,kotlin]
----
Body.empty()                         // the EmptyBody singleton
Body.text("hello")                   // raw text
Body.file(java.io.File("upload.bin")) // streamed file
Body.serialized(Item(1, "first"))    // captures the declared Item type
Body.serialized<List<Item?>>(listOf(Item(1, "first"), null))
Body.serialized<Item?>(null)
Body.serialized(listOf(Item(1, "first"), null), typeOf<List<Item?>?>())
----

`Body.serialized(value)` captures the full declared type through a reified type
parameter, including generic arguments and nullability. Specify the type argument
when you need a particular nullable or base type. The overload
`Body.serialized(value, type)` accepts an explicit `KType` for dynamically described
types. Both factories return `ObjectBody<T>` and defer serialization until request
execution. The existing body constructors remain available.

`Body.text("hello")` sends raw text; `Body.serialized("hello")` delegates to the
serializer (JSON encodes the string with quotes). For explicit types, supply the
full declared `KType` and ensure that it describes the value. The type argument of
a response handler must match its supplied `KType`.

The adapter uses the supplied `Json` configuration and its `SerializersModule` for
serializer lookup and conversion. Models require generated or custom serializers;
register contextual serializers in that module when needed. Serialization errors,
including missing serializers, reach the caller unchanged.

`ObjectResponseHandler` and `TypedResponseHandler` deserialize only statuses 200–299;
other statuses throw `IllegalStateException` before deserialization.
`RawResponseHandler` returns the original response for every status.

== HTTP behavior

`FunClient(serializer, strict = true)` rejects GET and DELETE requests with any body
other than `EmptyBody` by throwing `IllegalArgumentException` before serialization,
file reads or network execution. An explicitly empty `StringBody` is still a body.

Use `FunClient(serializer, strict = false)` when the target API explicitly supports
GET or DELETE bodies. This mode sends the supplied body, including streaming
`FileBody` uploads. Other methods behave identically in both modes. The client adds
no application-level retries. Request and response headers preserve multiple values.
`EmptyBody`, UTF-8 `StringBody`, `FileBody` and `ObjectBody` remain supported.

=== File uploads and byte ranges

`FileBody` describes a file or a byte range; the HTTP transport streams it without
loading the file into memory. The `Body` interface and `Body.file(file)` factory
are unchanged. Use the constructor for a range:

[source,kotlin]
----
FileBody(file)                           // entire file; same as Body.file(file)
FileBody(file, offset = 1024)             // from byte 1024 to the end
FileBody(file, offset = 1024, length = 512) // exactly 512 bytes
----

`offset: Long = 0` is zero-based and `length: Long? = null` means the remaining
bytes. Numeric arguments must be non-negative and their sum must not overflow
`Long`; violations throw `IllegalArgumentException` during construction.
Each execution checks that the path is a readable regular file, the offset is at
most the file size, and the range fits. Invalid bounds or a non-regular file throw
`IllegalArgumentException`; missing files and access/read failures throw `IOException`.
Zero length is valid anywhere up to and including the end of the file.

The transport fixes the range length before connecting and reports a known
content length, including zero. It seeks directly to the offset and reads only the
selected range using bounded buffers. Subsequent file growth does not add bytes.
Premature EOF, including truncation between validation and opening the stream,
fails the request with `EOFException` (possibly wrapped in an `IOException` by the
HTTP client). Resources are closed on completion, failure and cancellation.
Each subscription opens its own stream for the fixed range.

Keep the file unchanged while sending: the client does not snapshot its contents
or detect same-size modifications or truncation beyond the selected range.
Strict GET/DELETE rules also apply to empty file ranges, before file access.
Existing constructor calls remain source compatible, including the single-file
Java constructor. Adding data-class properties changes the binary signatures of
generated `copy` methods; recompile callers built against the former class.

== Build and publication

[source,shell]
----
./gradlew :funclient-core:test :funclient-core:build \
  :funclient-serializer:serializer-kotlinx:test \
  :funclient-serializer:serializer-kotlinx:build
git diff --check
----

`./gradlew build` also builds and tests both libraries. Both use the Java 21 toolchain.
Project, toolchain, plugin and dependency versions are centralized in
`gradle/libs.versions.toml`.
The publishing plugin prepares independent binary, sources and Maven
metadata for `net.igsoft:funclient-core:0.7.0` and
`net.igsoft:serializer-kotlinx:0.7.0`. The root and grouping project publish no library.
Remote publication uses the existing Maven Central signing and credential setup.
